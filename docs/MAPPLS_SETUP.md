# PICKR Mappls setup and navigation

Mappls is the only automatic map/search/routing provider. There is no silent Mapbox/Google/OSM routing fallback. On a routing failure the last successful route and its age remain visible, with an explicit stale/unavailable ETA. Maps require internet; this does not supply downloaded offline maps. Drivers can deliberately open Mappls or Google Maps externally. Those apps calculate their own routes; PICKR's recorded truck restrictions do not transfer through the links.

## Required account access

Set these in `.env.local` (or server hosting environment):

- `MAPPLS_REST_KEY`: server-only static key with standard Route ETA API Traffic access for the pilot. Search additionally requires geocoding and Place Details **Location Coordinates**. Predictive routing is optional and requires separate access. Restrict its use to your backend's IPs where practical.
- `MAPPLS_WEB_KEY`: separate browser-visible static key for Web Maps JS v3. Restrict it to the web domains you use, including localhost/LAN origins for testing and `https://appassets.androidplatform.net` for the Android bundled WebView. Confirm that Mappls accepts that WebView origin for your subscription. This key is intentionally delivered to authenticated clients; it is not a server secret.

Mappls changed authentication in August 2025. This integration uses the current documented static `access_token` APIs, not legacy OAuth client ID/secret exchanges. Predictive routing is access-controlled and time-based coverage varies by area. A default signup key may not provide all of the above. Confirm entitlements and permission to retain geocoded sites and route results with Mappls. Search requires numeric coordinates; if Place Details access is absent the UI explains this and permits manual map pins. It never substitutes a city centre.

Set `MAPPLS_ROUTING_MODE=standard` (default) for the currently allocated API. Set `predictive` only after that API is enabled; failures never silently switch modes.

Run `npm run pilot:setup`. It adds the new keys to an existing environment file when absent, applies three tracked migrations, and checks geocoding, both standard driving/trucking route endpoints and the SDK endpoint. Missing search coordinates are reported as a limitation rather than blocking map-pin testing. The SDK check from the server does not validate browser-domain restrictions. Enter actual truck measurements, then verify a `trucking` route in the driver app as well; setup deliberately does not invent a truck to pass that check.

If the first two migrations were already recorded by `pilot:setup`, rerunning applies only `20261010020000_mappls_navigation.sql`. Do not edit/reapply historical migrations. If earlier SQL was run manually, the setup runner detects the untracked schema and requires reconciliation rather than guessing that it matches. For the manual SQL workflow apply only the new migration to a project that already has the first two.

## Implemented behaviour

- Booking search and exact map pins use Mappls. The map displays active service polygons; the admin can draw/edit zones. Site entrances should be customer-confirmed.
- General road quotes request live traffic for immediate pickups. In standard mode even scheduled quotes use current traffic, not future traffic prediction. Predictive mode uses Kerala local departure time for scheduled quotes. Before assignment vehicle dimensions are unknown; the quote is labelled a general road estimate.
- Accepted trips route from the driver's current GPS to pickup. In-transit trips route from current GPS to destination. AT_PICKUP/AT_DROP display loading/unloading timers separately and do not claim a moving arrival ETA.
- Record actual overall height/width/length, maximum gross vehicle weight (vehicle plus load) and maximum axle load at onboarding. Full onboarding requires all five; testing skips may omit them. In predictive mode complete measurements use `profile=trucking` with explicit values, conservatively routing using maximum gross/axle weight. In standard mode complete measurements select only the generic trucking profile; the measured dimensions and weight are NOT applied. Standard mode labels that limitation and does not promise a traffic-optimal route. Missing measurements use a visibly labelled unrestricted road estimate. Cargo capacity is never substituted for gross weight, and provider default truck dimensions are never used for unknown vehicles. The driver's measurements cannot change during active work.
- The worker attempts refresh every 15 seconds; each active trip normally recalculates no more than once a minute. A route deviation over 100 m with GPS accuracy at most 50 m allows an earlier refresh, with a 20-second minimum between attempts. Worker provider calls are capped at four trips per pass. Larger fleets may need worker throughput tuning.
- Routing uses samples at most 60 seconds old and no worse than 150 m accuracy. Newer GPS samples still display independently of the cached route. Stale samples or estimates, provider failures and missing measurements are visible. A route older than 90 seconds is stale; a failure marks the cached ETA stale immediately. The displayed arrival is the absolute time estimated at the last calculation, not a GPS extrapolation.
- Database leases deduplicate refreshes across worker/manual checks. Stage/assignment checks discard late responses. Quote distance fares remain locked; route refreshes do not reprice the booking. Existing waiting charges still apply independently.
- Mappls's map traffic control is enabled for available traffic layers. No invented green/red congestion overlay is drawn from ETA changes.
- Drivers can report closure/flooding/accident/congestion/site-access problems at a selected map point. Driver reports stay pending until admin verification. Admin can create, verify or dismiss reports under **roads**. In predictive mode verified nearby closures/flooding are sent as avoidance locations on the next route calculation. In standard mode all reports are advisory and automatic avoidance is unavailable; other categories are advisory. Reports expire after two hours and must be submitted again if still relevant. Avoidance requests depend on Mappls road matching and are not guarantees that the reported road will be excluded.
- Mappls traffic affects ETA, but **a separate Mappls incident-report feed is not connected**. Its documented Route Events Summary plugin expects a route ID from a different direction flow; the predictive API used here documents no compatible route ID. Once Mappls confirms a compatible entitlement/API contract it can be added. The app explicitly identifies local reports as operator-verified reports; it does not present them as a comprehensive live-event feed.
- External navigation remains a practical turn-by-turn option. In-app native turn-by-turn guidance, voice manoeuvres, lane/junction navigation and offline maps are not implemented. Mappls routing returns route instructions, but they are not run as a navigation SDK.

## Field checks before hauling

Start with an empty truck on known Thrissur roads. Validate the route to pickup, stage switch to destination, ETA updates, screen-off GPS while using external navigation, and deliberate deviation. Check provider restrictions against actual bridge/road signs and site entrances. Test a verified temporary road closure and dismiss it after testing; check route refresh and automatic expiry. Turn off mobile data/GPS and confirm stale warnings without fabricated motion. Test map access on both the web origin and the Android WebView origin. Do not infer Kerala street-level traffic/event coverage from an API returning HTTP 200.

Primary references: [Web Maps JS v3](https://developer.mappls.com/documentation/sdk/Web/Web%20JS/), [Predictive/live traffic and trucking](https://developer.mappls.com/documentation/sdk/rest-apis/mappls-predictive-routing-api/readme/), [Geocoding](https://developer.mappls.com/documentation/sdk/rest-apis/mappls-maps-geocoding-rest-api-example/Readme/), [Place Details/coordinate entitlement](https://developer.mappls.com/documentation/sdk/rest-apis/mappls-maps-place-details-api-example/Readme/), [External Mappls directions](https://developer.mappls.com/mappls-apps/mappls-app/), [Route Events Summary plugin](https://developer.mappls.com/documentation/sdk/Web/Mappls%20Web%20Plugins/routesummary/readme/).

Mappls resolves to IPv4 and IPv6. The IPv4-only cloud whitelist initially caused 401 responses on the laptop’s IPv6 connection. `pilot:start` and `pilot:setup` now prefer IPv4 DNS results; a forced IPv4 routing request succeeded with the saved whitelist. If launching Next directly instead, set `NODE_OPTIONS=--dns-result-order=ipv4first` or configure the corresponding verified IPv6 allowlist. No TLS checks are disabled.

After domain restrictions, the SDK endpoint returns 200 for the Android app origin but rejects local HTTP localhost/LAN origins with IP/Domain validation failed (401). Port and full-origin variants did not resolve this; the saved list retains host names. `pilot:setup` checks the SDK with the actual Android origin headers rather than a server request lacking a Referer. This is an endpoint check, not physical-device map rendering. Local web maps require provider clarification or an approved HTTPS origin.
