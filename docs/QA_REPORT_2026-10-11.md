# PICKR implementation and QA report — 11 October 2026

## Verdict

The core booking workflow is working in the hosted backend, browser and installed Android pilot APKs. A native customer booking completed quote → dispatch → driver acceptance → pickup/loading → transit → delivery/unloading → cash confirmation, and the driver became available again. Separate backend tests exercised private photos, direct UPI confirmation, cancellation restrictions, competing drivers, service areas and permission boundaries.

This supports a supervised pilot with known drivers. It is **not an unrestricted public-launch sign-off**: address search remains blocked by Mappls Place Details coordinate access; remote Firebase push is not configured; predictive/truck-restricted routing and traffic incident feeds are unavailable with current entitlements. Physical-phone GPS/background behaviour and real Malayalam speech still require field testing. Passing API tests does not mean every UI option has been exercised on every device.

No real load or payment was made. Cash/UPI entries were explicitly labelled QA confirmations. Tests used isolated Bangalore sites, synthetic documents/photos and emulator GPS; existing customer work was not accepted or cancelled.

## Test scope and evidence

- Unit/regression suite: **62 tests, 10 suites passed**; ESLint clean; Next production build and both Vite/Gradle APK builds passed. New geofence tests cover valid, closed, concave, collapsed, duplicate and crossed boundaries. Existing price, selection, lifecycle, origin and session tests remain passing.
- Hosted environment: https://pickr-xueh.onrender.com; real Supabase/Postgres/storage and Mappls standard route/traffic ETA. Five pilot migrations applied. No fabricated route distance or ETA was substituted.
- Android: `PICKR_QA` Pixel 5 emulator, Android API 35, ARM64, 1080×2340 at density 440; separate customer/driver APKs, version 0.6.0-pilot/code 6, roughly 3 MB each. Used the test-android-apps emulator QA skill, fresh UI XML bounds for taps, screenshots and crash-buffer inspection.
- Browser: hosted customer manual booking/draft/review and profiles; admin controls; real SDK map pin selection. A requested 360px viewport override did not change the observed customer viewport (734px); therefore **360px browser coverage is not claimed**. The emulator covers approximately 393dp. Temporary viewport override was reset.
- Search-radius test advanced clocks only on owned QA booking rows and invoked dispatch for all five rounds. It verifies algorithm/state transitions, not five minutes of real elapsed timing.
- Crash buffer contained a UiAutomation “Bad file descriptor” failure in the test tooling. No PICKR application fatal stack was found in the captured buffer. This is not a long-duration stability or performance certification.

API/control results follow. PASS means the asserted response/state was observed. FIXED records an initial failure with a separate successful retest. BLOCKED identifies unavailable provider access, not a passing fallback. Evidence is condensed; sanitized raw results are in `artifacts/comprehensive-qa-results.json` after cleanup.

## Test cleanup and repeatability

Only labelled QA rows were changed. Original settings are restored, Bangalore QA boundary retained **inactive**, QA customers/drivers soft-deactivated with sessions revoked, driver services stopped, and the QA road report dismissed. Test trip/upload records remain for audit rather than being permanently purged. Thrissur remains the active pilot; the existing non-QA searching trip was not acted on.

The opt-in harness is `scripts/qa-pilot.mjs`; it reads local environment credentials without printing them and uses the versioned synthetic `tests/fixtures/qa-load.png`. It guards against other online/assigned drivers and test-phone collisions. It is not a production cron job: `init`, `run`, `extended`, then **cleanup** must be run deliberately in a suitable isolated environment. Tests use shared settings briefly and should not be rerun while real assigned work is in progress. Current fixed test phones already exist as disabled audit accounts; a future run needs a fresh test namespace/project. Native UI evidence and sanitized result JSON are local artifacts, not credentials.

Final APKs target the hosted HTTPS backend out of the box. Install both files, permit precise driver location/notifications, use real test drivers in Thrissur, and validate the remaining physical-phone cases with an operator before allowing unattended trips.
